Metrics

Warum zwei Metric-Pipelines?

pod_level

Fuer Targets, die einem Pod oder Service zugeordnet werden koennen. Hier ist Kubernetes-Enrichment sinnvoll.

alloy, annotation_autodiscovery, ServiceMonitors

meta_level

Fuer Exporter und Infrastrukturquellen. KSM-Metriken beschreiben andere Workloads und duerfen nicht die Labels des KSM-Pods bekommen.

ksm, node_exporter, kubelet, cadvisor

Metric Filtering

Wo filtere ich Metriken?

Global

Wenn eine Metrik generell nie exportiert werden soll.

alloyPipeline:
  metrics:
    globalDropRegex: "go_.*|process_.*"
    globalKeepRegex: ""

Pro Target

Wenn nur eine Quelle betroffen ist, z.B. kubelet oder cAdvisor.

prometheus.relabel "drop_unwanted" {
  rule {
    source_labels = ["__name__"]
    regex = "container_network_.*"
    action = "drop"
  }
}
OTTL

Warum gibt es metric/log/trace statements?

OTel hat unterschiedliche Datenmodelle. Logs haben einen Body, Spans haben Span-Attribute, Metrics haben Metric- und Datapoint-Kontexte. Deshalb muss Alloy getrennte Statement-Bloecke rendern.

Runtime

Getrennte Kontexte sind technisch notwendig.

GitOps-Code

Gemeinsame Regeln liegen trotzdem einmal in _ottl.tpl.

Praxis

Ein neues globales Resource-Label wird im Helper ergaenzt, nicht dreimal kopiert.

Logs

Loki braucht wenige Labels, nicht alle Labels

Loki-Cardinality entsteht ueber Stream Labels. Deshalb setzt das Deployment nur wenige Resource Labels fuer Loki und behaelt Details als Attribute.

loki.resource.labels = "cluster, namespace, job, pod"

Gut

Cluster, Namespace, Job, Pod.

Riskant

User IDs, Request IDs, full URLs, Container Image IDs.

Merksatz

Was viele Werte hat, gehoert nicht automatisch in den Index.

Export

Exporter sind Backpressure- und Reliability-Grenzen

Processed Signalbereinigt und angereichert
ExporterOTLP HTTP oder gRPC
Sending Queuepersistent auf Disk
Retrytransiente Fehler abfangen
BackendMimir, Loki, Tempo, Elastic

Batching steckt in der Exporter-Queue. Ein zusaetzlicher Batch-Processor ist hier nicht das Zielbild.

Best Practices

Regeln, die man sich merken sollte

Pipeline-Reihenfolge

  • Memory limiter frueh.
  • Enrichment vor Redaction.
  • Mapping nach sauberer Identity.
  • Exporter mit Queue und Retry.

Ownership

  • Neues Target: neues Scrape-Modul.
  • Globale Labels: OTTL Helper.
  • Metric Policy: Values oder Target-Relabel.
  • Backend-Details: destinations.
Validierung

Nie nur YAML anschauen. Immer rendern und Alloy validieren.

helm template alloy apps/alloy/noctua \
  -n alloy \
  -f apps/alloy/base/values.yaml \
  -f apps/alloy/noctua/values.yaml \
  > /tmp/alloy-noctua-render.yaml

alloy validate --stability.level=public-preview \
  /tmp/alloy-noctua-validate/config.alloy

helm lint apps/alloy/noctua \
  -f apps/alloy/base/values.yaml \
  -f apps/alloy/noctua/values.yaml

kubeconform -summary -ignore-missing-schemas \
  /tmp/alloy-noctua-render.yaml
Entscheidung

Das Zielbild ist nicht weniger Funktion. Es ist weniger versteckte Funktion.

`k8s-monitoring` bleibt die Quelle fuer gutes Kubernetes-Monitoring-Wissen. Das Noctua-Deployment macht dieses Wissen explizit, modular, reviewbar und validierbar.
